## Главный вывод: ядро платформы уже написано — внутри Petid.care

Ожидаемый вывод такого разбора — «надо построить общую платформу». Данные говорят другое. Из 32 общих механизмов **лучшая реализация 14 уже лежит в Petid.care**, ещё 7 — в DOKI. Ядро не нужно проектировать с нуля: его нужно **извлечь** из двух продуктов, которые де-факто стали инженерным центром компании.

Второй вывод, менее приятный: часть дублирования — это не беспорядок, а **риск**. Одна и та же защита реализована по-разному, и слабые варианты живут в проде.

Для каждого механизма выбиралась сильнейшая существующая реализация — по полноте, изоляции за интерфейсом и наличию тестов. Распределение резко неравномерное, и это главный факт для планирования.

## Дублирование, которое является риском, а не беспорядком

1. **Защита от открытого редиректа — четыре разных механизма.**
   Канон (Petid) нормализует адрес через разбор URL относительно контрольного origin и отбрасывает управляющие символы. Варианты со сравнением строк **пропускают обходы** — например `/\evil.com` и закодированные переводы строк. Три реализации из четырёх слабее канона.

2. **Лимиты запросов: десять реализаций, часть открывается при сбое.**
   Канон (Petid) — устойчивое окно за SECURITY DEFINER RPC с закрытым RLS и ленивой очисткой. В ArchiDom миграция лимитов **написана, но не применена в проде**, то есть защита публичных форм там сейчас не работает вообще.

3. **Согласия на обработку данных — одиннадцать точек, разные правила.**
   Компания работает под двумя режимами сразу: 152-ФЗ для русскоязычных продуктов и индонезийский PDP для балийских. Только канон (Petid) одновременно переиспользуем, версионирует политику вместе с текстом и пишет серверную запись. Разъезжающиеся согласия — юридический риск, а не стилистика.

4. **Двенадцать LLM-клиентов и разные политики по персональным данным.**
   Маскирование данных до вызова модели есть **только в двух продуктах из трёх, которые вызывают модели**. При этом в DOKI по умолчанию предпочитается провайдер, про который в его же конфиге написано, что данные уходят за пределы страны — для сейфа с паспортами это отдельный риск. Один шлюз с единой политикой решает это архитектурно.

## Что должно стать общим: десять пакетов, ноль сервисов

Ранее девять модулей были названы «сервисами». После разбора кода это уточняется: **сегодня ни один из них не должен быть отдельным сервисом.** Всё, что нужно — библиотеки с одним владельцем.

Сервис оправдан, когда есть состояние или секреты, ≥3 потребителя *и* боль, которую библиотека не снимает: отдельное масштабирование, отдельный релизный цикл, отдельная юрисдикция. Такой боли пока нет ни у одного модуля.

### Десять пакетов — делать

| Пакет | Содержание | Донор |
| --- | --- | --- |
| `supabase` | серверный, браузерный, service-role и анонимный клиенты + проверка настроек | PET + OB |
| `auth` | гейт middleware, колбэк входа, безопасный редирект, ролевой гейт, шаблон RLS-хелперов | PET + DOK |
| `forms` | лимиты, приманка, согласия, E.164, шестизначный код | PET + VIL + DOK |
| `notify` | адаптеры каналов: почта, Telegram, WhatsApp Cloud, сборщик `wa.me` | PET + KOR + OB |
| `llm` | `completeJSON`, ремонт JSON, реестр промптов, маскирование данных, гейт эндпоинта | ARH + DOK + PET |
| `tokens` | выдача, проверка, срок, отзыв, пароль, журнал доступа | DOK |
| `events` | события с белым списком и payload без персональных данных | OB |
| `i18n` | типизированные словари, разрешение локали, alternates | PET |
| `seo` | граф `@id`, sitemap, hreflang, пинг индексации | KOR |
| `booking-core` | чистое ядро доступности без ввода-вывода, адаптеры по продуктам | KOR |

### Два кандидата в сервисы — потом

- **Шлюз LLM** станет сервисом, когда появится вторая юрисдикция хранения (перенос данных РФ) или когда понадобится общий бюджет и лимиты на модели поверх продуктов. Триггер — юридический, не технический.
- **Токены и QR** станут сервисом, когда скан QR получит внешнее обещание по времени ответа и защите от перебора — например при массовом использовании потерявшихся питомцев.

До этих триггеров оба живут как пакеты. Триггеры стоит записать в реестр решений, чтобы к вопросу не возвращаться раз в месяц.

### Как извлекать

- Не начинать с монорепо-миграции. Начать с **одного приватного пакета и трёх семейств**: лимиты, согласия, уведомления.
- Переносить **вместе с тестами**. Канон выбирался по полноте и наличию тестов — без них перенос теряет смысл.
- Первым потребителем делать **не Petid**, а второй продукт: только так проверяется, что интерфейс не прирос к донору.
- Продуктовые словари, доменные правила и схемы остаются в продуктах. Общими становятся **механизмы**, а не содержание.

## Границы достоверности

Проверочный проход по дублированию **не выполнен**: все пять верификаторов упали по лимиту доступа. Пути и состав семейств собирались с проверкой существования файлов, но **выбор «канонической» реализации — это суждение агента**. Перед извлечением каждого пакета его донора нужно просмотреть глазами: пятнадцать минут ревью на пакет против переноса неудачного эталона во все продукты.

**Чего здесь нет.** Дублирование доменной логики (меню, паспорта проектов, медицинские записи) не искалось — оно и не должно быть общим. Также не оценивались TablePilot, Doki.id, Makeup.cafe и ZubiLook: их репозиториев в разборе не было, хотя часть найденных механизмов почти наверняка повторяется и там.
